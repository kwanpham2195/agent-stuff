# Feature playbook

Use for an authorized change to user-visible behavior. Follow the [entrypoint](../SKILL.md) for lifecycle and permissions.

1. Reuse the issue, accepted design, and observable success criteria. Use [define-outcome](../../define-outcome/SKILL.md) when product intent is incomplete. Pause for consequential user choices before implementing the uncertain part.
2. Inspect the relevant implementation, callers, tests, and repository instructions. Use RPI's research steps for a remaining consequential question. When past decisions constrain the feature, read the [historical investigation reference](../../references/historical-investigation.md).
3. For a substantial behavior change, use [show-me](../../show-me/SKILL.md) to show the proposed user flow or concrete input/output before implementing. Compare consequential alternatives when a decision is needed; otherwise continue within scope. If a durable design or phased plan is warranted, propose the [write-design-doc](../../write-design-doc/SKILL.md) skill or a proportional plan under [work lifecycle](../../references/work-lifecycle.md#plan-act-verify-accept) and obtain agreement. Reuse an accepted plan rather than creating another.
4. Implement the smallest slice that satisfies the agreed criteria. Follow [coding standards](../../coding-standards/SKILL.md) for shared rules and applicable language additions, and [discoverable code](../../coding-standards/references/discoverable-code.md) for naming.
5. Run required repository checks and exercise the changed user path with the existing project verification skill or documented tooling. Cover relevant failure cases and side effects. When performance is a criterion and the change adds work the old version did not do, judge it by an absolute budget for the added work and the user-visible end state, not a ratio against the old version. If verification tooling is missing, report the gap and offer the [create-verification-skill](../../create-verification-skill/SKILL.md) skill when reusable control would help; generating a skill is separate work requiring agreement.
6. Review the diff against the outcome and standards, using [code-review](../../code-review/SKILL.md) when review is requested or warranted by risk. Use its [impact analysis reference](../../code-review/references/impact-analysis.md) for consequential assumptions. Resolve findings within scope and report evidence against acceptance. Required human review remains pending until the user responds.

For a retrospective, offer [retro](../../retro/SKILL.md) only when requested or useful to discuss observed friction. Publishing, commits, and verification-skill maintenance retain their own authorization.
