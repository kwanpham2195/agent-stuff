# Diagnostics

Use for bugs, crashes, slow paths, leaks and traces. Follow the [entrypoint](../SKILL.md) for lifecycle and permissions.

Follow [work lifecycle](../../references/work-lifecycle.md#plan-act-verify-accept) for diagnostic evidence and verification. Reproduce the original scenario and verify the fix on the same surface/profile using the actual browser (`agent-browser`) or terminal (`terminal-control`) owner. Distinguish observed results from source inference and report blocked runtime proof.

Fix the first place the system went wrong, not the place the symptom surfaced. Ask whether the triggering state is legitimate. If the system may be in that state, handle it where the code broke. If the state should never exist, a guard there hides the bug, so find what produced the state. When a failure appears only after a restart, check persisted state first, such as config, caches and lock files. Search for the same fault elsewhere. Fix every instance within the task's scope and report the rest. If a workaround needs a paragraph-long comment to justify it, fix the code instead. Remove changes made for a hypothesis that runtime evidence refuted. After two fixes that share a premise fail the same gate, write the premise down and test it directly before a third fix.

For a captured trace or heap snapshot, reduce it to queryable rows, one per sample, frame or node, and trace hot frames or retainers to source. A leak diagnosis needs the retainer chain from the leaked object to a GC root. Confirm a cause by diffing captures from before and after the fix. Without that pair, call the cause the strongest hypothesis the capture supports.

When the question is what happens if events arrive in another order, such as a retry after a timeout, two callers at once or a write that lands after the caller gave up, model the flow and check every order with a state-machine checker when one is available. Use it for that question only. A test answers a mapping, validation or straight-line question better. Iterate in a scratch folder, then store what the skill produced in the owning work item's `evidence/<yyyymmdd>-<slug>/` under [context routing](../../references/context-routing.md#work-metadata-and-overview): the spec, config and view module, the generated chart and report, the checker output, the rendered SVG and the command that regenerates them. Add a short README with the question, the results and the assumptions the model makes. Link the bundle from the finding that cites it. When no work item owns the question, choose or create one under context routing. The repository gets none of it. Report the shortest bug path in the code's words, then replay it against the real code, and suspect the model first when the bug does not occur. File the lasting finding as a rule or open question in the repository's existing docs and tests, and add no model to the repository unless the same flow keeps failing. When it does, ask the user before adding a project skill that verifies that flow, because it needs upkeep.
