# Refactoring playbook

Use for an authorized structural improvement. Follow the [entrypoint](../SKILL.md) for lifecycle and permissions.

1. Name the concrete maintenance problem and the behavior that must remain unchanged. Read the affected callers, tests, and public contracts. If the request changes behavior too, separate that decision using [define-outcome](../../define-outcome/SKILL.md) before choosing an implementation.
2. Establish a baseline with relevant existing checks. If intent or compatibility depends on past changes, use [historical investigation](../../references/historical-investigation.md). Ask before removing functionality that appears intentional. Missing tests do not prove that a behavior is unused. When exact visual equivalence is an agreed criterion, capture screenshots of each affected component in each of its states before changing it. Without that baseline, make no parity claim. Never edit the baseline to make a comparison pass.
3. Use [show-me](../../show-me/SKILL.md) to sketch current and proposed structure, including preserved contracts. Identify affected boundaries using [impact analysis](../../code-review/references/impact-analysis.md). Compare consequential alternatives when a decision is needed; otherwise continue within scope. If phased execution is warranted, propose a proportional plan under [work lifecycle](../../references/work-lifecycle.md#plan-act-verify-accept) and obtain agreement; keep small work inline.
4. Refactor a coherent slice under [coding standards](../../coding-standards/SKILL.md) and [discoverable code](../../write-discoverable-code/SKILL.md). Apply the linked shared rules and applicable language additions. Avoid unrelated cleanup or new abstractions without a concrete need.
5. Compare behavior before and after through affected callers and required repository checks. After a rename or move, search for the old name in strings, docs, configuration and links, which symbol-aware tools miss. Add a focused regression or characterization test when it protects a consequential contract. Use the existing project verification tooling for live behavior; report blocked proof without claiming equivalence from static inspection.
6. Review the final diff for behavior changes, scope, and standards using [code-review](../../code-review/SKILL.md) when warranted. Report the structural improvement, preserved contracts and evidence, intentional approved behavior changes, and residual uncertainty.
